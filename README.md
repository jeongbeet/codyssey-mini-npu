# Mini NPU Simulator

입력 패턴과 두 필터의 MAC(Multiply-Accumulate) 점수를 계산하고, 큰 점수의
필터를 선택하는 Python 콘솔 애플리케이션입니다. 사용자 입력, JSON 일괄 분석,
허용오차에 따른 동점 판정, 크기별 성능 측정, 실패 원인 요약을 제공합니다.

MAC은 NumPy 등 외부 라이브러리 없이 이중 반복문으로 구현했습니다.
`main.py`는 실행 진입점이며, 실제 구현은 `src/` 패키지에 있습니다.
실행할 때 `main.py`, `src/`, `data.json`을 같은 저장소 안에 유지하세요.

## 실행 방법

- 필요 환경: Python 3.10 이상.
- 검증 환경: Python 3.12.14, Linux x86_64.
- 의존성: Python 표준 라이브러리만 사용하므로 추가 패키지 설치가 필요 없습니다.
- 아래 명령은 저장소 루트에서 실행합니다. 환경에 따라 `python` 대신 `python3`를 사용하세요.

대화형 메뉴:

~~~bash
python main.py
~~~

~~~text
Mini NPU Simulator
1. 사용자 입력 (3×3)
2. data.json 분석
0. 종료
~~~

각 분석이 끝나면 메뉴로 돌아옵니다. 메뉴에서 잘못된 값을 입력하면 다시 선택할 수 있습니다.

메뉴를 거치지 않고 한 번 실행:

~~~bash
python main.py --mode manual
python main.py --mode json
python main.py --mode json --data data.json --epsilon 1e-9 --repeats 1000
~~~

같은 프로그램을 패키지로 실행할 수도 있습니다.

~~~bash
python -m src --mode json
python main.py --help
~~~

기본 JSON 경로는 실행 위치와 관계없이 저장소의 `data.json`입니다.
`--data`로 지정한 상대 경로는 현재 작업 디렉터리를 기준으로 해석합니다.

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--mode` | 대화형 메뉴 | `manual`: 3×3 입력, `json`: JSON 분석 |
| `--data` | 저장소의 `data.json` | 분석할 JSON 파일 |
| `--epsilon` | `1e-9` | 동점 판정에 사용하는 양의 유한한 절대오차 |
| `--repeats` | `100` | 필터별 측정 횟수. 최소 10회 |

제공된 데이터에는 동점으로 인해 FAIL인 케이스가 3개 있습니다.
따라서 `--mode json`으로 실행하면 결과를 모두 출력한 후 **종료 코드 1**을 반환합니다.

| 종료 코드 | 의미 |
|---|---|
| `0` | 사용자 입력 모드 완료, JSON 전체 PASS, 또는 메뉴에서 정상 종료 |
| `1` | JSON 분석 완료 후 FAIL인 케이스가 하나 이상 존재 |
| `2` | 잘못된 옵션, 파일·최상위 스키마 오류, 미완료 행렬 입력, 사용자 모드 연산 오류 |
| `130` | 사용자가 Ctrl+C로 중단 |

개별 케이스의 크기·라벨·필터 오류는 해당 케이스의 FAIL로 집계합니다.
대화형 메뉴에서는 파일 오류를 안내한 후에도 다음 모드를 선택할 수 있습니다.

## 사용자 입력 모드: 3×3

실행 순서는 다음과 같습니다.

1. 필터 A를 3줄로 입력합니다.
2. 필터 B를 3줄로 입력합니다.
3. 저장된 필터 A와 B를 출력하여 확인합니다.
4. 패턴을 3줄로 입력합니다.
5. 두 MAC 점수와 각 MAC 호출 시간(ms)을 계산합니다.
6. A/B/UNDECIDED 판정과 3×3 반복 성능 측정 결과를 출력합니다.

각 줄에는 공백으로 구분한 숫자 3개가 필요합니다.
각 행렬은 정확히 3행을 받으며, 행별 숫자 개수나 숫자 변환에 문제가 있으면
해당 행을 다시 입력합니다. 정수·소수·음수를 지원하고 NaN과 무한대는 거부합니다.
입력이 중간에 끝나면 오류 메시지를 출력하고 종료합니다.

예시 필터 A:

~~~text
0 1 0
1 1 1
0 1 0
~~~

예시 필터 B:

~~~text
1 0 1
0 1 0
1 0 1
~~~

예시 패턴:

~~~text
0 1 0
1 1 1
0 1 0
~~~

이 입력의 결과는 **A 점수 5, B 점수 1, 판정 A**입니다.
시간은 실행 시 측정한 값으로 출력합니다.
동점이면 `UNDECIDED (판정 불가)`를 출력합니다.
사용자 입력 모드에는 expected가 없으므로 PASS/FAIL 정답 비교는 수행하지 않습니다.

## JSON 분석 모드

첨부된 원본 `data.json`을 내용 변경 없이 포함했습니다.
최상위에는 `meta`, `filters`, `patterns`가 있으며, `meta`는 계산에 사용하지 않습니다.
`filters`와 비어 있지 않은 `patterns` 객체가 필수입니다.

| 구분 | 제공 데이터의 구조 |
|---|---|
| `filters.size_5` | `cross`, `x`에 각각 5×5 필터 |
| `filters.size_13` | `cross`, `x`에 각각 13×13 필터 |
| `filters.size_25` | `cross`, `x`에 각각 25×25 필터 |
| `patterns.size_5_1`, `patterns.size_5_2` | `input`: 5×5 패턴, `expected`: 정답 라벨 |
| `patterns.size_13_1`, `patterns.size_13_2` | `input`: 13×13 패턴, `expected`: 정답 라벨 |
| `patterns.size_25_1`, `patterns.size_25_2` | `input`: 25×25 패턴, `expected`: 정답 라벨 |

케이스 키는 `size_{N}_{idx}` 형식입니다. N은 양의 정수이고 idx는 숫자입니다.
키에서 추출한 N으로 `filters["size_N"]`을 선택하며,
패턴과 두 필터 모두 정확히 N행·N열인지 검사합니다.
행렬은 2차원 리스트로 저장하므로 `matrix[row][col]`로 값을 읽거나 수정할 수 있습니다.
실수로 변환할 수 있는 범위의 정수·실수만 허용하며 문자열 숫자, bool, NaN, 무한대는 거부합니다.

라벨은 입력 위치에 관계없이 아래 표에 따라 정규화하며, 앞뒤 공백과 대소문자도 처리합니다.

| 원본 라벨 | 내부 표준 라벨 |
|---|---|
| expected의 `+` | `Cross` |
| 필터의 `cross`, 표준 표기 `Cross` | `Cross` |
| expected/필터의 `x`, 표준 표기 `X` | `X` |

정규화 후 Cross와 X 필터가 모두 있어야 합니다.
지원하지 않는 라벨이나 정규화 후 중복된 필터 라벨도 검증 오류입니다.
`UNDECIDED`는 계산 결과의 동점 상태이며 expected의 정답 라벨로 허용하지 않습니다.

JSON 모드의 흐름:

1. 파일을 읽고 최상위 스키마를 검증합니다.
2. 케이스 키에서 크기를 추출하고 필터를 선택합니다.
3. expected와 필터 이름을 정규화하고 행렬 크기·값을 검증합니다.
4. Cross/X 점수를 계산하고 epsilon 정책으로 판정합니다.
5. 정규화한 expected와 판정 결과를 비교하여 PASS/FAIL을 출력합니다.
6. 3×3·5×5·13×13·25×25 성능 표를 출력합니다.
7. 전체 테스트 수·통과 수·실패 수 및 실패 식별자·사유를 요약합니다.

개별 케이스의 검증 오류나 MAC 결과의 오버플로는 FAIL로 남기고 다음 케이스를 계속 처리합니다.
연산하지 못한 케이스의 점수·판정은 `-`로 표시하여 동점과 구별합니다.
파일 없음, JSON 문법 오류, 최상위 필수 객체 누락, 빈 patterns는 전체 로드 오류로 안내합니다.
0개 케이스를 실행하고 성공한 것으로 보고하지 않습니다.

## MAC과 epsilon 정책

점수는 다음과 같습니다.

~~~text
score = Σ(row=0..N-1) Σ(col=0..N-1) pattern[row][col] × kernel[row][col]
~~~

`src/mac.py`에서 검증된 두 행렬을 이중 반복문으로 순회하고,
행 참조를 `pattern_row`, `kernel_row`에 보관한 뒤
`total += pattern_row[col] * kernel_row[col]`로 점수를 누적합니다.
0인 원소도 순회하며, 필터의 배율이나 점수를 임의로 정규화하지 않습니다.

~~~python
if abs(score_a - score_b) < epsilon:
    decision = "UNDECIDED"
else:
    decision = label_a if score_a > score_b else label_b
~~~

- 기본 epsilon은 절대오차 `1e-9`입니다.
- 차이가 epsilon보다 작으면 동점입니다. 정확히 같으면 큰 점수를 선택합니다.
- 판정에는 반올림 전 float 값을 사용합니다.
- 화면 점수는 최대 12자리 유효숫자로 표시하고, 동점 사유에는 점수 차이를 최대 17자리로 표시합니다.
- 사용자 모드는 A/B, JSON 모드는 Cross/X를 판정 라벨로 사용합니다.
- expected는 점수 계산이나 판정에 사용하지 않고, 판정 후 정답 비교에만 사용합니다.
- JSON에서 UNDECIDED는 expected인 Cross/X와 다르므로 FAIL입니다.
- epsilon을 변경하면 동점 여부와 집계 결과가 달라질 수 있습니다.

## 성능 측정 방법

`time.perf_counter_ns()`로 MAC 함수 호출 구간만 측정합니다.
각 필터를 한 번 워밍업한 뒤 필터별 최소 10회, 기본 100회를 측정합니다.
입력, 출력, 파일 읽기, 행렬 생성, 검증, 워밍업은 측정 시간에 포함하지 않습니다.

~~~text
평균 시간(ms) = 모든 측정 구간의 합(ns) / (필터 수 × 반복 횟수) / 1,000,000
~~~

두 필터를 각각 측정해 합산하므로 표의 시간은 **필터 하나에 대한 MAC 함수 1회 평균**입니다.
사용자 모드에서 따로 출력하는 A/B 시간은 각각 단일 호출의 실측값입니다.

JSON 모드에서는 크기별로 계산 가능한 첫 번째 케이스를 성능 측정에 사용합니다.
동점이나 정답 불일치인 케이스도 정상적으로 점수가 계산되었다면 사용할 수 있습니다.
JSON에 없는 3×3, 또는 사용할 수 있는 케이스가 없는 크기는 고정된 측정용 행렬을 생성합니다.
측정용 생성 데이터는 결과에 출처를 표시하며 JSON 테스트 합계에 포함하지 않습니다.

N²는 곱셈 후 누적하는 MAC 단계의 개수입니다.
곱셈과 덧셈을 각각 별도 산술 연산으로 세면 필터 하나에 2N²회입니다.
두 필터를 비교하는 판정 한 건은 2N² MAC 단계를 수행합니다.

### 실패 원인 및 복잡도 분석

1. 제공된 데이터의 패턴은 크기별 2개씩 총 6개이며, 6개 모두 스키마 검증과 MAC 계산을 완료했습니다.
2. 필터·패턴의 행·열 수는 모두 일치하므로 이번 실행에는 크기 오류로 인한 FAIL이 없습니다.
3. 원본 expected의 `+`, `x`와 필터 이름 `cross`, `x`는 Cross/X로 정규화했습니다.
4. 정규화를 통해 표기가 다른 동일 라벨을 같게 비교하며, 라벨 불일치 자체로 발생하는 오판을 방지했습니다.
5. `size_5_1`의 점수는 Cross=0.9, X=0.8999999999999999이며 차이는 약 `1.1102230246251565e-16`입니다.
6. 이 차이는 epsilon보다 작아 UNDECIDED이며, expected=X와 일치하지 않아 FAIL입니다.
7. `size_13_2`의 점수는 Cross=7.499999999999997, X=7.5이며 차이는 약 `2.6645352591003757e-15`입니다.
8. 이 케이스도 epsilon 기준 동점이므로 UNDECIDED이며, expected=Cross와 일치하지 않아 FAIL입니다.
9. `size_25_1`의 점수는 Cross=4.9, X=4.899999999999999이며 차이는 약 `1.7763568394002505e-15`입니다.
10. 이 케이스 역시 UNDECIDED이며, expected=X와 일치하지 않아 FAIL입니다.
11. 세 차이는 부동소수점 표현·누적 오차 수준입니다. 단순 대소 비교로 특정 라벨을 선택하지 않도록 epsilon 정책을 적용했습니다.
12. 따라서 세 실패는 유효한 입력에서 동점 판정과 expected가 불일치한 결과입니다. expected에 맞추기 위해 필터나 판정 규칙을 바꾸지 않았습니다.
13. `size_5_2`, `size_13_1`, `size_25_2`는 충분한 점수 차이가 있으며 각각 Cross, X, Cross로 판정되어 PASS입니다.
14. JSON 테스트 집계는 실제 패턴 6개만 포함하며, 3×3 측정용 데이터와 성능 반복 호출은 포함하지 않습니다.
15. MAC 함수는 N행마다 N열을 모두 처리하므로 시간 복잡도는 O(N²)입니다.
16. 두 필터의 점수를 계산하면 2N² MAC 단계를 수행하지만 상수 계수를 제외한 복잡도는 O(N²)입니다.
17. 크기가 N_k인 K개 케이스의 검증·판정 시간은 전체 입력량에 비례하는 O(ΣN_k²)이며, 파일 파싱과 결과 출력 시간은 별도입니다.
18. 반복 성능 측정은 두 필터와 반복 횟수 R에 대해 O(R·ΣN²)이고, 표에는 반복 합계가 아닌 호출 1회 평균을 기록했습니다.
19. MAC 함수는 누적 변수와 반복 인덱스만 사용하므로 이미 저장된 입력을 제외한 추가 공간은 O(1)입니다.
20. 행렬 한 개의 저장·검증 복사 공간은 O(N²)이며, 전체 JSON은 파일 내용과 행렬들을 메모리에 보관합니다.
21. 작은 행렬에서는 타이머·함수 호출 비용과 시스템 부하의 영향이 상대적으로 커서 실측 시간의 비율이 N² 비율과 정확히 같지는 않습니다.
22. 자동화 테스트 40개는 모두 통과했습니다. 이 검증에는 제공 데이터의 3개 FAIL을 올바르게 보고하는 동작도 포함됩니다.

## 라벨 추가 절차 — 평가 항목 #18

현재 판정 클래스는 Cross와 X 두 개입니다.
`src/data_loader.py`의 `LABEL_ALIASES`가 원본 표기와 표준 라벨을 연결하고,
`STANDARD_LABELS`가 필수 필터 집합을 정의합니다.
별칭 하나를 추가하는 경우와 Circle처럼 판정 클래스를 추가하는 경우의 변경 범위는 다릅니다.

### 기존 클래스의 별칭 추가

1. **정규화:** 예를 들어 향후 `plus`를 Cross의 별칭으로 지원하려면
   `LABEL_ALIASES`에 `"plus": "Cross"`를 추가합니다. 키는 소문자로 등록합니다.
   `normalize_label()`이 공백·대소문자를 처리하며 expected와 필터 키에 함께 적용합니다.
2. **검증·판정:** `STANDARD_LABELS`와 MAC·epsilon 규칙은 유지합니다.
   `cross`와 `plus` 필터를 동시에 제공하면 같은 Cross로 정규화되므로 중복 오류여야 합니다.
3. **출력:** `CaseResult`와 `print_case_result()`에는 표준 라벨 Cross가 전달되어야 합니다.
   원본 별칭을 정답 비교나 결과 출력에 다시 사용하지 않습니다.
4. **테스트:** `normalize_label(" PLUS ") == "Cross"`, expected/필터 키 양쪽의 별칭,
   중복 별칭 거부, 기존 Cross/X 데이터의 결과를 확인합니다.
   `tests/test_data_loader.py`의 `test_new_alias_is_shared_by_expected_and_filter_keys`는
   임시 별칭을 주입해 이 경로를 검증합니다. 기본 입력 별칭 목록에는 아직 plus가 없습니다.

## 1000×1000 처리와 메모리 제한 — 평가 항목 #19

1000×1000 행렬에는 원소가 1,000,000개 있습니다.
필터 하나는 1,000,000 MAC 단계, 두 필터 판정은 2,000,000 MAC 단계를 수행합니다.
기본 100회씩 반복하면 측정에만 200,000,000 MAC 단계가 필요하므로,
대형 입력의 탐색적 측정은 최소 기준을 충족하는 `--repeats 10`으로 시작하는 것이 적절합니다.

### 재현 가능한 시간·메모리 진단

`src/profiling.py`는 진단용 치밀 행렬 3개를 생성하고 생성·검증·MAC 시간을 분리합니다.
각 원소를 별도의 float 객체로 만들어 같은 상수 객체를 공유할 때의 메모리 과소평가를 피합니다.
원본 JSON 판정이나 테스트 집계에는 이 데이터를 추가하지 않습니다.

~~~bash
python -m src.profiling --size 1000 --repeats 10 --memory-budget-mib 256
~~~

- 시간 측정은 워밍업을 제외한 필터별 10회, 총 20회 MAC 호출의 평균입니다.
- 입력 생성과 검증 시간은 각각 3개 행렬을 한 번 처리한 시간입니다.
- 시간 측정을 마친 뒤 해당 입력을 해제하고, 별도 실행에서 `tracemalloc` 할당 최고치를 측정합니다.
- 메모리 예산은 입력 생성 전에 검사하여 큰 입력의 할당을 거부할 수 있습니다.
  예를 들어 위 명령에서 `--memory-budget-mib 1`이면 행렬을 만들기 전에 종료 코드 2를 반환합니다.
- 예산 추정에는 3개 float 행렬, 검증용 리스트 복사본, 리스트 여유 공간과 추가 여유를 포함합니다.
  이 생성 데이터에서 `float(float_value)`는 기존 float 객체를 재사용하므로 검증은 주로 참조 버퍼를 추가합니다.
- 이 검사는 진단 명령의 **Python 할당 추정치**입니다. 프로세스 RSS의 하드 제한이나
  일반 `main.py` JSON 로더의 메모리 제한은 아닙니다. 추적기 자체·인터프리터·외부 할당은 별도입니다.

Python 3.12.14 / Linux x86_64에서 2026-11-17에 동일 진단기로 측정한 결과입니다.
수정 전은 `e295e73`의 MAC·검증 구현, 수정 후는 행 참조 재사용과 오류 문자열 지연 생성을 적용한 구현입니다.

| 입력 3개 검증 1회 | 846.014423 ms | 476.199669 ms |
| MAC 함수 1회 평균 | 45.123026 ms | 34.611613 ms |

### 현재 적용한 최적화와 추가 확장 방향

| 항목 | 현재 적용 또는 권장 절차 | 제약·검증 기준 |
|---|---|---|
| MAC 행 참조 재사용 | `mac_score()`에서 각 행의 참조를 한 번 읽고 열 반복에서 재사용 | 이중 인덱싱을 줄임. 전체 행 우선 누적 순서와 O(N²)는 유지 |
| 검증 비용 감소 | 정상 원소마다 만들던 행·열 위치 문자열을 오류가 발생했을 때만 생성 | 숫자·크기 검증 및 오류 위치 표시는 유지 |
| 행 블록 처리 | 향후 B=64행씩 읽기 → 검증 → MAC 누적 → 버퍼 해제 순서로 처리 | 입력 전체가 이미 메모리에 있으면 블록 연산만으로 전체 메모리가 줄지 않음 |
| 데이터 읽기 | 대형 데이터용 JSONL/행 블록 파일 어댑터를 별도로 구현하고 순차 로드 | 현재 `json.load()`는 전체 파일을 읽음. 현재 구현을 스트리밍 로더로 간주하면 안 됨 |
| 필터 재사용 | 크기별 필터를 한 번 검증하여 불변 입력으로 재사용하는 캐시를 도입 | 현재는 케이스별 검증. 크기·내용 변경 시 캐시 무효화 및 잘못된 필터의 실패 전파 테스트 필요 |
| 압축된 숫자 저장 | 표준 라이브러리 `array('d')`·`mmap` 등 연속 저장을 별도 백엔드로 검토 | 타입·스키마 검증 API 조정과 변환 비용 측정 필요. NumPy를 도입하지 않음 |
| 멀티스레드 | 일반 CPython 3.12의 CPU 반복문에는 ThreadPoolExecutor 속도 향상을 기대하지 않음 | GIL로 Python 바이트코드가 직렬 실행됨. I/O 대기 겹치기에는 활용 가능 |
| 멀티프로세스 | 독립 케이스를 프로세스로 분산하고 큰 입력은 공유 메모리/파일 매핑으로 전달 | 프로세스 생성·직렬화·전송·결과 병합까지 포함해 순이익 측정. 작업자 수는 CPU 할당량과 메모리 예산으로 제한 |
| 실제 메모리 제한 | 컨테이너/cgroup 메모리 제한을 설정하고 입력·검증 복사·작업자·IPC·파서용 여유를 확보 | 이 저장소의 진단 예산만으로 OOM을 완전히 막을 수는 없음 |

64비트 CPython에서 독립 float 객체가 원소마다 있으면 값 약 24바이트와 리스트 참조 약 8바이트가 필요합니다.
따라서 1000×1000 행렬 하나는 리스트 헤더·여유 용량을 제외해도 약 30.5 MiB이고,
패턴과 필터 둘로 이루어진 3개 행렬에는 약 91.6 MiB 이상이 필요합니다.
실측 119.38 MiB에는 여기에 검증 복사본 등이 더해졌습니다.
반면 연속 float64의 숫자 데이터만은 행렬당 약 7.63 MiB입니다.
문자열 JSON 버퍼, 파서 객체, 정수를 float로 새로 변환할 때의 객체도 추가로 고려해야 합니다.

행 블록을 실제 입력 스트리밍과 함께 사용하면 작업 버퍼는 O(B·N)으로 제한할 수 있습니다.
예를 들어 N=1000, B=64의 두 연속 float64 입력 버퍼는 약 0.98 MiB입니다.
Python 리스트·float 표현에서는 같은 두 버퍼도 헤더를 제외해 약 3.91 MiB가 필요합니다.
블록마다 별도 부분합을 만든 뒤 다시 더하면 부동소수점 덧셈 순서가 달라집니다.
기존 결과를 유지하려면 블록 경계를 넘어 하나의 누적 변수로 행 우선 순서를 유지하고,
비순차 병렬 합산을 도입할 경우 epsilon 경계·취소 오차 사례를 별도로 검증해야 합니다.

벡터화/SIMD는 네이티브 CPU 구현에서 고려할 수 있는 설계 대안입니다.
현재 과제 구현은 NumPy 등 외부 연산 라이브러리를 사용하지 않고 Python 반복문을 유지합니다.

## CPU와 NPU의 병목 비교 — 평가 항목 #20

이 프로그램은 CPU에서 실행되는 MAC 알고리즘 시뮬레이터입니다.
위 시간은 CPU의 Python 실행 실측이며 실제 NPU 장치의 성능 수치가 아닙니다.
CPU 하드웨어도 SIMD·멀티코어 병렬 처리가 가능하지만 현재 Python 루프는 이를 직접 활용하지 않습니다.

| 관점 | 현재 CPU/Python 구현 | 실제 NPU 실행에서 확인할 점 |
|---|---|---|
| MAC 병렬성 | 단일 누적 변수에 직렬로 곱셈·덧셈. 인터프리터와 boxed float 비용 발생 | 여러 MAC 연산기를 병렬 구동하되 최종 합산·동기화 비용 존재 |
| 데이터 배치 | 리스트 참조와 분리된 float 객체 접근 | 보통 연속 텐서와 타일을 사용. 온칩 SRAM 크기와 정렬·타일 크기 제약 |
| 메모리 대역폭 | 반복 인덱싱·객체 접근·캐시 미스 비용이 더해짐 | 병렬 MAC에 데이터를 공급할 DRAM/SRAM 대역폭이 부족하면 연산기가 대기 |
| 전송·실행 준비 | 입력 파싱과 검증 후 함수 호출 | 호스트↔장치 전송, 커널 실행 준비, 결과 복사 비용을 따로 측정 |
| 유리한 작업 | 작은 입력은 장치 전송이 없고 제어 흐름이 간단함 | 충분히 큰 작업·배치와 필터/패턴 재사용이 있어야 전송 비용을 상쇄하기 쉬움 |
| 수치 정책 | Python float와 고정된 누적 순서, 절대 epsilon=1e-9 | FP16/INT8 등 지원 정밀도·양자화·병렬 합산 순서에 따라 오차가 달라짐 |

**병목 예측과 실측 해석:** 1000×1000 수정 전의 첫 판정에서는 생성 약 391ms,
검증 약 846ms, 두 필터 MAC 약 90ms가 필요했습니다.
입력을 처음 준비하는 경로에서는 검증이 가장 큰 측정 구간이며,
검증된 입력을 반복 처리하는 경로에서는 MAC 루프가 중심 비용입니다.
이를 근거로 검증 문자열 생성과 반복 인덱싱을 먼저 줄였습니다.
이 시간 구분만으로 하드웨어 메모리 대역폭이 포화됐다고 단정할 수는 없습니다.

필터 하나에 대해 두 입력을 각각 한 번 읽는 연속 float64 모델이라면,
1000×1000에서 약 16 MB를 읽고 곱셈+덧셈 2,000,000회를 수행합니다.
산술 집약도는 약 `2 / (2 × 8) = 0.125 FLOP/byte`로 낮습니다.
이는 캐시 재사용을 제외한 단순 모델이며 Python 객체의 실제 트래픽 측정값은 아닙니다.
입력 재사용이 적은 연산을 NPU로 옮기면 높은 MAC 처리량보다 데이터 공급·전송이 제한 요인이 될 수 있습니다.
FP16/INT8 장치는 바이트 수와 연산 단위가 달라지므로 해당 장치의 정밀도로 모델을 다시 계산해야 합니다.

완화 방안은 단계별로 확인합니다.

1. **CPU:** 생성·검증·MAC·I/O 구간을 분리해 시간을 기록하고, 현재 적용한 최적화로 실제로 줄어든 구간을 확인합니다.
2. **메모리:** 입력 크기와 작업자 수를 늘릴 때 할당 최고치·RSS·IPC 버퍼를 함께 점검합니다.
   반복되는 입력 복사와 필터 재검증을 줄이고, 큰 데이터는 행 블록 로드와 연속 저장을 검토합니다.
3. **NPU:** 실제 장치에서는 호스트 전송, 장치 연산, 결과 복사 시간을 각각 재고
   배치·온칩 필터 재사용·DMA와 연산의 겹치기로 전체 지연시간이 줄어드는지 확인합니다.
   단일 커널 시간만으로 CPU보다 빠르다고 결론 내리지 않습니다.
4. **정확도:** 하드웨어 백엔드 추가나 부분합 병렬화는 누적 순서·정밀도가 바뀔 수 있습니다.
   기존 float/epsilon 기준 결과와 비교한 뒤 허용 정책을 명시적으로 결정해야 하며,
   현재 기준을 통과시키기 위해 epsilon을 임의로 바꾸지 않습니다.
