# Mini NPU Simulator

두 필터 중 어느 쪽이 입력 패턴에 더 잘 맞는지 MAC(Multiply-Accumulate) 점수로 비교하는 Python 콘솔 프로그램입니다. 3×3 필터를 직접 입력해 보거나, 예제 파일에 담긴 십자(Cross)와 X자(X) 패턴을 한꺼번에 판정할 수 있습니다.

## 실행 방법

Python 3.10 이상에서 저장소 루트로 이동해 실행하세요. 표준 라이브러리만 사용합니다.

```bash
python main.py                           # 1 직접 입력 · 2 JSON 분석 · 3 패턴 생성 · 0 종료
python main.py --mode manual             # 3×3 필터와 패턴을 직접 입력
python main.py --mode json               # 저장소의 data.json 분석
python main.py --mode generate --size 5  # 5×5 Cross와 X 생성 및 성능 비교
```

`python -m src`로도 같은 메뉴를 열 수 있습니다. 다른 JSON 파일은 `--data 경로`로 지정하고, 전체 옵션은 `--help`에서 확인하세요.

### 3×3 직접 입력

필터 A의 세 줄, 필터 B의 세 줄을 차례로 입력합니다. 저장된 필터가 화면에 나오면 같은 방식으로 패턴을 입력하세요. 한 줄에는 공백으로 구분한 유한한 숫자 세 개가 들어갑니다. 개수가 다르거나 숫자로 읽을 수 없으면 그 줄만 다시 받습니다.

| 입력 순서 | 첫째 줄 | 둘째 줄 | 셋째 줄 |
|---|---|---|---|
| 필터 A | `0 1 0` | `1 1 1` | `0 1 0` |
| 필터 B | `1 0 1` | `0 1 0` | `1 0 1` |
| 패턴 | `0 1 0` | `1 1 1` | `0 1 0` |

이 예시에서 패턴의 1은 A와 다섯 칸, B와는 가운데 한 칸만 겹칩니다. **A 점수는 5, B 점수는 1이므로 판정은 A**입니다. 화면에서 각 필터의 계산 시간(ms)과 3×3 반복 측정 평균도 볼 수 있습니다.

### Cross와 X 자동 생성

메뉴에서 **3**을 고르고 크기 N을 입력하면 두 모양을 모두 볼 수 있습니다. Cross는 가운데 행과 열을, X는 양쪽 대각선을 1로 채웁니다. N은 양의 정수이며, 짝수 크기의 Cross는 가운데 두 줄 중 아래쪽 행과 오른쪽 열을 씁니다. 1×1에서는 두 모양이 모두 `[1]`입니다. 생성기는 각 모양을 차례로 입력 패턴으로 삼아 같은 필터 쌍으로 성능을 측정합니다.

직접 입력 모드에서도 **각 행렬의 첫 줄**에 `cross` 또는 `x`를 쓰면 그 행렬을 자동으로 채웁니다. 예를 들어 `python main.py --mode manual --size 5`에서 필터 A, 필터 B, 패턴에 각각 `cross`, `x`, `x`를 입력해 보세요. 패턴이 A와는 한 칸, B와는 아홉 칸 겹쳐 **1 대 9로 B**가 선택됩니다. 필터는 직접 입력하고 패턴만 생성해도 됩니다.

### JSON 일괄 분석

`data.json`의 `filters`에는 크기별 필터 쌍이, `patterns`에는 패턴(`input`)과 정답(`expected`)이 들어 있습니다. 패턴 키는 `size_{N}_{idx}` 형식입니다. 예를 들어 `size_13_2`를 읽으면 `filters["size_13"]`에서 두 필터를 꺼내 패턴과 필터가 모두 13×13인지 확인합니다.

필터 이름과 정답은 앞뒤 공백과 대소문자를 정리한 뒤 `+`와 `cross`를 `Cross`로, `x`를 `X`로 통일합니다. 행렬에는 유한한 정수와 실수만 허용합니다.

크기가 다르거나 필터가 빠졌을 때, 알 수 없는 라벨이나 중복 라벨이 나왔을 때는 해당 케이스에 FAIL 사유를 남기고 다음 패턴으로 넘어갑니다. 파일을 읽을 수 없거나 최상위 형식이 잘못된 경우, 또는 패턴이 하나도 없는 경우에는 파일 오류를 표시합니다.

## 점수 계산과 동점 판정

MAC은 패턴과 필터에서 같은 위치의 두 값을 곱해 모두 더한 값입니다. 직접 입력과 JSON 판정에서는 검증된 행렬을 행 순서대로 **길이 N²인 1차원 리스트**로 펼칩니다. 예를 들어 `[[1, 2], [3, 4]]`는 `[1, 2, 3, 4]`가 됩니다. 패턴과 필터를 나란히 읽으며 한 반복문에서 곱해 더하므로 2차원 이중 반복문과 누적 순서가 같습니다. 두 구현 모두 Python 표준 라이브러리만 쓰며, 판정에는 반올림 전 점수를 사용합니다.

동점 조건은 **`abs(score_a - score_b) < epsilon`**입니다. 기본 허용오차는 `1e-9`이며 `--epsilon`으로 양의 유한한 값을 지정할 수 있습니다. 차이가 허용오차보다 작으면 `UNDECIDED`(판정 불가), 정확히 같거나 크면 점수가 높은 필터를 선택합니다. JSON의 `expected`는 이 판정이 끝난 뒤 PASS/FAIL을 매길 때 사용합니다.

## 결과 리포트

예제 파일의 5×5, 13×13, 25×25 패턴은 크기별로 두 개씩입니다.
여섯 건 모두 크기와 라벨 검사를 통과했고, 정답과 비교한 결과는 **3 PASS / 3 FAIL**입니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | 정답 | 결과 |
|---|---:|---:|---|---|---|
| `size_5_1` | 0.9 | 0.9 | UNDECIDED | X | FAIL |
| `size_5_2` | 8.9 | 0.1 | Cross | Cross | PASS |
| `size_13_1` | 0.3 | 14.7 | X | X | PASS |
| `size_13_2` | 7.5 | 7.5 | UNDECIDED | Cross | FAIL |
| `size_25_1` | 4.9 | 4.9 | UNDECIDED | X | FAIL |
| `size_25_2` | 52.9 | 0.1 | Cross | Cross | PASS |

### 동점 세 건이 FAIL인 이유

`size_5_1`에서 Cross 점수는 가운데 한 칸의 0.9점입니다. X 점수는 대각선 아홉 칸의 0.1점을 더한 값입니다.
반복문으로 0.1을 아홉 번 더하면 `0.8999999999999999`가 되어 두 점수 사이에 약 `1.11e-16`의 차이가 생깁니다.

`size_13_2`도 0.3을 25번 더한 값과 7.5를 비교합니다. `size_25_1`에서는 4.9와 0.1을 49번 더한 값을 비교합니다.
점수 차이는 각각 약 `2.66e-15`, `1.78e-15`입니다.
세 케이스 모두 차이가 허용오차보다 작아서 `UNDECIDED`가 되고, 정답으로 지정된 Cross나 X와 달라 FAIL입니다.

그래서 예제 파일로 `--mode json`을 실행하면 요약과 실패 목록을 출력한 뒤 종료 코드 `1`을 반환합니다. 전체 PASS이거나 메뉴에서 정상 종료하면 `0`, 입력·파일·옵션 오류로 실행을 마치면 `2`, Ctrl+C로 중단하면 `130`입니다.

### 같은 입력으로 비교한 2차원·1차원 MAC

직접 입력·JSON 분석·패턴 생성 모드 모두 같은 패턴과 필터로 두 구현을 비교합니다. 2D는 행과 열을 순회하고 1D는 한 번 펼친 리스트를 재사용합니다. 필터마다 두 구현을 한 번씩 워밍업하면서 점수가 같은지 확인한 뒤, 먼저 측정할 구현을 회차마다 바꿉니다. `perf_counter_ns()`로 MAC 호출만 재고, 패턴과 필터를 펼치는 데 걸린 시간은 따로 표시합니다.

아래는 `python main.py --mode json --repeats 1000`으로 측정한 결과입니다(Python 3.12.14, Linux x86_64, 2026-11-22). 반복 횟수의 기본값은 필터당 100회, 최소는 10회입니다. 여기서는 각 구현에서 두 필터를 각각 1,000회 호출하고 총시간을 2,000으로 나눴습니다.

| 크기 | MAC 횟수(N²) | 2D 평균(ms) | 1D 평균(ms) | 2D/1D | 한 번 펼치는 시간(ms) |
|---|---:|---:|---:|---:|---:|
| 3×3 | 9 | 0.000591 | 0.000509 | 1.16 | 0.001743 |
| 5×5 | 25 | 0.001107 | 0.000980 | 1.13 | 0.002564 |
| 13×13 | 169 | 0.005536 | 0.005011 | 1.10 | 0.009054 |
| 25×25 | 625 | 0.017163 | 0.018701 | 0.92 | 0.020010 |

2D/1D가 1보다 크면 1D 호출이 빠릅니다. 이 실행에서는 13×13까지 1D가 빨랐고, 25×25에서는 2D가 빨랐습니다. 한 번만 판정할 때는 패턴과 두 필터의 변환 시간도 함께 고려해야 합니다. 입력을 여러 번 쓰면 그 비용을 나눠 부담할 수 있습니다.

3×3은 예제 JSON에 없어 성능 측정용으로만 생성합니다. 패턴 하나를 판정할 때 두 필터를 적용하므로 총 MAC 횟수는 **2N²**, 시간 복잡도는 **O(N²)**입니다.
5×5에서 25×25로 커지면 연산 횟수는 25배가 됩니다. 작은 행렬에서는 함수 호출과 타이머 비용도 측정값에 영향을 줍니다.
행렬 저장과 검증용 복사, 1차원 리스트 생성에는 각각 O(N²) 공간이 들고, 준비된 입력을 순회하는 MAC 자체의 추가 공간은 O(1)입니다.

## 새 라벨을 추가하려면

기존 Cross에 `plus`라는 별칭을 주려면 `src/data_loader.py`의 `LABEL_ALIASES`에 `"plus": "Cross"`를 추가합니다. 필터 키와 정답이 모두 `normalize_label()`을 거치므로 두 곳에서 같은 표기를 쓸 수 있습니다. `plus`와 `cross` 필터를 함께 넣으면 중복으로 처리되는지도 확인하세요.

세 번째 필터로 `Circle`을 도입할 때는 다음 순서로 확장합니다.

1. **정규화와 입력** — `o`와 `circle`을 `Circle`에 연결합니다. 새 데이터에 크기별 Circle 필터와 정답 패턴을 넣고, `prepare_case()`가 데이터 형식에 맞는 필터 집합을 검사하도록 합니다. 기존 파일의 기본값은 `STANDARD_LABELS`에 있는 Cross와 X입니다.
2. **판정** — `evaluate_case()`에서 모든 필터 점수를 구해 1위와 2위의 차이에 epsilon을 적용합니다. 하위 점수끼리 동점이어도 1위가 충분히 앞서면 그 라벨이 이깁니다.
3. **출력** — `CaseResult`에 라벨별 점수를 담고 `print_case_result()`에서 점수·판정·정답을 출력합니다. 성능 측정에도 실제 필터 목록을 넘깁니다.
4. **테스트** — 새 별칭, 중복·누락 필터, Circle 단독 승리, 상위·하위 동점, epsilon 경계와 출력까지 확인합니다. 마지막으로 기존 A/B 입력과 예제 여섯 건을 다시 실행합니다.

## 1000×1000 행렬의 시간과 메모리

1000×1000에서는 필터 한 장에 곱셈·누산이 100만 번 필요합니다. 아래 명령은 2차원 기준 구현에서 행렬 생성·검증·MAC 시간과 메모리를 측정합니다.

```bash
python -m src.profiling --size 1000 --repeats 10 --memory-budget-mib 256
```

| 측정 구간 | 개선 전 (`e295e73`) | 개선 후 (`a65b7c2`) |
|---|---:|---:|
| 행렬 3개 생성 | 391.41 ms | 532.60 ms |
| 행렬 3개 검증 | 846.01 ms | 476.20 ms |
| MAC 1회 평균 | 45.12 ms | 34.61 ms |
| Python 할당 최고치 | 119.38 MiB | 119.38 MiB |

각 버전을 같은 환경에서 한 차례 실행한 기록입니다. 검증할 때는 오류가 난 원소에만 행·열 안내 문구를 만들고, MAC 루프에서는 한 번 읽은 행을 재사용하면서 두 구간의 시간이 줄었습니다. 시간은 실행마다 달라질 수 있습니다.

메모리는 시간을 잰 뒤 별도 실행에서 `tracemalloc`으로 측정합니다. 위 입력의 행렬과 검증용 복사본에 대한 사전 추정치는 **157.83 MiB**입니다. 진단기는 이 추정치가 예산을 넘으면 행렬을 만들기 전에 멈춥니다. 프로세스 전체의 메모리 상한은 컨테이너 등 실행 환경에서 설정합니다.

현재는 `json.load()`가 파일 전체를 메모리에 올립니다. 입력을 B행씩(예를 들어 64행씩) 읽을 수 있게 바꾸고, 읽은 행을 검증하고 누적한 뒤 버퍼를 비우면 작업 공간은 O(B·N)으로 줄어듭니다. 블록이 바뀌어도 같은 변수에 행 순서대로 더해야 동점 근처에서 계산 결과가 재현됩니다.

1000×1000 행렬 한 장을 `array('d')` 같은 연속 float64 버퍼에 담으면 숫자 데이터는 7.63 MiB입니다. 이런 배치는 네이티브 CPU 코드에서 여러 칸을 한 번에 계산하는 벡터화(SIMD)에도 적합합니다. 현재 CPython 3.12 반복문에서는 GIL 때문에 멀티스레드의 이점이 주로 I/O 대기에 있습니다. 독립 케이스를 여러 프로세스로 나눈다면 공유 메모리로 복사를 줄이고, 전송 시간과 작업자별 메모리를 함께 재야 합니다.

## CPU와 NPU의 병목

이 앱의 CPU 구현에서는 한 칸씩 곱해 점수 하나에 차례로 더합니다. 위 측정에서는 행렬 세 장을 검증하는 데 약 476 ms, 준비된 입력에 두 필터를 적용하는 데 약 69 ms가 들었습니다. 같은 크기의 패턴을 연달아 처리한다면 이미 검증한 필터를 재사용해 준비 시간을 줄일 수 있습니다.

NPU에서는 여러 MAC 연산기가 병렬로 동작해도 데이터를 공급하는 메모리 대역폭이 성능을 제한할 수 있습니다. 예를 들어 두 float64 값을 한 번씩 읽어 곱하고 더하면 16바이트당 산술 연산은 두 번뿐입니다(0.125 FLOP/byte). 실제 장치에서 비교할 때는 호스트 전송·장치 연산·결과 복사를 각각 재고, 여러 패턴을 묶거나 필터를 온칩 메모리에서 재사용할 때 전체 시간이 어떻게 달라지는지 확인합니다. FP16이나 INT8을 쓰면 누적 정밀도도 달라지므로 동점 경계의 판정까지 함께 비교해야 합니다.
